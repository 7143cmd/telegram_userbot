# Архітектура та вибір технологічного стеку

Опис архітектурних рішеннь, використані під час розробки системы автономних Telegram-юзерботів.

---

## 1. Чому обрано саме таку архітектуру

Для реалізації імітації живого спілкування в групі була обрана **подієво-орієнтована (Event-Driven) асинхронна архітектура** на базі фреймворку `Telethon` та асинхронного драйвера `asyncio`.

### Основні причини вибору:

* **Event-Driven підхід (Telethon Events):**
  Замість постійного опитування сервера (polling), боти реагують на події в реальному часі (`events.NewMessage`). Це забезпечує мінімальну затримку при обробці повідомлень і зменшує навантаження на мережу.
* **Асинхронність (`asyncio`):**
  Оскільки система керує кількома Telegram-сесіями паралельно, асинхронність дозволяє виконувати мережеві запити к API Telegram, звернення до LLM Groq та таймаути імітації набору тексту (`typing...`) не блокуючи головний потік виконання.
* **Централізоване керування станом (`GroupState`):**
  Стан кожної групи (активна тема, ID стартового повідомлення, черга спікерів) винесено в окремий об'єкт. Це запобігає стану гонитви (race conditions) за допомогою `asyncio.Lock`.
* **Використання Groq API (Qwen 3.8 27B):**
  Забезпечує високу швидкість генерації відповідей (high throughput / low latency), що критично важливо для збереження природного темпу діалогу в чаті.

---

## 2. Переваги обраного підходу

1. **Масштабованість:** Додавання нових ботів або нових груп відбувається через конфігураційні файли без зміни ядра логіки.
2. **Надійність:** Використання файлів `.session` та `.json` дозволяє ізолювати кожен акаунт.
3. **Ефективне використання ресурсів:** Однопотокова асинхронна модель споживає мінімум оперативної пам'яті навіть при роботі з десятком акаунтів.
